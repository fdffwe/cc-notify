# Claude Code 通知工具（WSL → Windows）开发任务清单

> 目标：在 WSL 中运行，当 Claude Code 发生关键事件（等待授权、任务完成）时，向 Windows 发送原生通知。
>
> 日期：2026-10-10

---

## 第 0 步：确认需求与环境摸底

**做什么**：确认三件事——
1. 触发时机：Claude Code 的 `Notification` hook（等待授权/空闲提醒）、`Stop` hook（任务完成）是否都要覆盖？
2. 通知形式：Windows 原生 toast 弹窗？声音？还是先弹窗后说？
3. Windows 侧可用的通道：在 WSL 里跑 `powershell.exe -Command "echo ok"` 验证互操作是否正常。

**为什么**：WSL→Windows 通知有多个方案（powershell.exe + BurntToast、wsl-notify-send.exe、msg.exe），通道是否可用直接决定技术路线。

**验收**：能用一句话说清"什么事件 → 什么通知形式"，且 `powershell.exe` 可从 WSL 调用。

---

## 第 1 步：最小可运行版（MVP）—— 手动触发一条 toast

**做什么**：写一个 shell 脚本（如 `notify.sh`），接收标题和消息两个参数，通过 `powershell.exe` 弹出一条 Windows toast（先用最简单的方式，比如 `[Windows.UI.Notifications.ToastNotificationManager]` 或 `msg.exe`，不引入依赖）。

**为什么**：先打通"WSL 脚本 → Windows 弹窗"这条链路，这是整个工具的核心风险点。链路不通，后面一切免谈。

**验收**：终端执行 `./notify.sh "标题" "内容"`，Windows 屏幕右下角出现通知。

---

## 第 2 步：接入 Claude Code hooks

**做什么**：在项目或用户级 `settings.json` 中配置 `Notification` 和 `Stop` 两个 hook，指向 notify 脚本，并把 Claude Code 传入的参数（如消息内容）正确转发给脚本。

**为什么**：这一步把"手动弹窗"变成"事件驱动"，工具才算真正服务于 Claude Code 工作流。

**验收**：
- 让 Claude Code 执行一个需要权限确认的操作 → Windows 收到"等待授权"通知；
- 让它完成一个任务 → 收到"任务完成"通知。

---

## 第 3 步：健壮性处理

**做什么**：
- 超时保护：hook 阻塞会卡住 Claude Code，脚本要快速退出（powershell.exe 首次调用较慢，考虑后台执行 `&` 或加 timeout）；
- 失败静默：通知失败不应影响主流程，错误只写日志不抛出；
- 特殊字符转义：消息内容可能含引号、换行，传给 powershell 前要转义（安全相关，防注入）。

**为什么**：hook 是同步链路上的一环，任何卡顿或报错都会直接影响 Claude Code 体验。

**验收**：消息含引号/中文/换行时不崩溃；人为让通知失败（如改名 powershell 路径）后 Claude Code 依然正常工作。

---

## 第 4 步：体验优化（可选，按需排序）

**做什么**：
- 区分事件类型：Notification 和 Stop 用不同标题/图标/声音；
- 加点击聚焦：点击通知跳转到对应终端窗口（BurntToast 支持，需 Windows 侧装模块）；
- 防打扰：短时间内重复事件做合并或静音。

**为什么**：基础版够用后再提升体验，避免过早优化。

**验收**：不同事件有可区分的通知表现。

---

## 建议的节奏

第 0→3 步是必做主线，做完即完整可用的 v1；第 4 步迭代。
最终产物：1 个通知脚本 + 1 份 Claude Code hooks 配置，规模很小。
